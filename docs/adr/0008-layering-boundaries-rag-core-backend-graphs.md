# ADR-0008: 공유 RAG Core, 백엔드 API, LangGraph 간의 역할 경계 정립 및 모듈 레이어링 규칙 수립

* **작성일 (Date)**: 2026-06-19
* **상태 (Status)**: 승인됨 (Accepted)

---

## 맥락 (Context)
- 본 프로젝트는 모노레포 환경에서 공유 RAG 라이브러리인 `packages/rag-core`, 지식 베이스 및 데이터 처리를 담당하는 `apps/backend`, 그리고 대화 흐름을 제어하는 `packages/graphs` (Aegra 서빙 대상 LangGraph)로 다층적 패키지 구성을 취하고 있음.
- 프로젝트 초기에는 `rag-core`가 단순히 공유 유틸리티 모음으로 다루어졌으나, 쿼리 재작성, 트리 요약, 의도 분류 등 점진적으로 고도화된 기능들이 구현되면서 각 처리가 어떤 컴포넌트 내부에서 실행되어야 하는지에 대한 경계선이 모호해짐 (일명 '아키텍처 회색지대' 발생).
- 특히, 지식 베이스 검색(Retrieval) 시 LangGraph(`graphs`)가 Vector DB(Qdrant)나 관계형 DB(PostgreSQL)에 직접 드라이버를 통해 달라붙어 연결할 경우 다음과 같은 문제가 수반됨:
  1. **설정 및 환경의 중복**: DB 연결 주소, 포트, 인증 크레덴셜 정보가 백엔드 서버뿐만 아니라 그래프 서빙 서버(Aegra)에도 복제되어 구성 동기화와 보안 관리가 어려워짐.
  2. **의존성 비대화**: 그래프 패키지가 대량의 데이터베이스 클라이언트, 무거운 ORM 프레임워크 등을 함께 설치하게 됨.
- 따라서, 백엔드의 역할과 LangGraph의 오케스트레이션 책임 범위를 선명히 분리하고, 앞으로 개발자와 AI 어시스턴트 모두가 기능 추가 시 혼란 없이 동일한 디자인 패턴을 따르도록 가이드라인 규칙을 확립해야 함.

---

## 결정 (Decision)
> **요약**: DB/벡터스토어 커넥션 세션 및 물리 자원 제어가 필요한 **상태성(Stateful) 데이터 영역**은 모두 백엔드가 소유하고, 그래프는 백엔드의 HTTP API를 통해서만 데이터에 접근하도록 경계를 제한함. 반면, 데이터베이스 연결이 필요 없는 **무상태성(Stateless) LLM 호출 및 연산 유틸리티**는 `rag_core` 라이브러리를 통해 백엔드와 그래프 두 레이어 모두에서 직접 임포트하여 인프로세스(In-process)로 독립 실행할 수 있도록 허용함.

### 2.1. 물리 데이터 저장소 접근의 백엔드 단일화 (Backend-Only Stateful Operations)
- **DB 직접 접근 금지**: LangGraph 컴포넌트(`packages/graphs`) 내부에서는 `qdrant_client`, `sqlalchemy` 등 데이터베이스 전용 드라이버를 임포트하거나 세션을 생성할 수 없음.
- **검색 API 연동**: 지식 베이스 검색은 백엔드에서 표준 API로 노출하는 `/api/v1/knowledge_bases/search` 엔드포인트를 호출하여 결과를 반환받는 것으로 일원화함. 그래프 런타임은 DB의 물리적 스키마나 인덱스 구성을 알 필요 없이 JSON 규격 데이터만 취급함.

### 2.2. 무상태 RAG 유틸리티의 공유 라이브러리 직접 활용 (Shared Stateless Core Utilities)
- **무상태 모듈 설계**: 쿼리 재작성(`QueryRewriter`), 트리 요약(`TreeSummarizer`), 동의어 확장(`SynonymExpander`), 인용 검증(`CitationValidator`) 등의 비즈니스 로직은 외부 DB 세션을 요구하지 않는 순수 함수 혹은 LLM 호출형 컴포넌트로 설계하여 `rag_core`에 구현함.
- **그래프 직접 임포트 및 실행**: 그래프 서빙 서버는 `rag-core`에서 해당 무상태 모듈들을 임포트하여 그래프 노드 내부에서 직접 인스턴스화하고 실행함.
  - 이를 통해 그래프 오케스트레이터가 직접 LLM 게이트웨이(LiteLLM)와 다이렉트로 통신하고, 네이티브 토큰 스트리밍 응답을 중간 프록시 병목 없이 즉시 클라이언트에게 제공할 수 있도록 제어권을 확보함.

### 2.3. 의존성 경계 문서화 및 어시스턴트 가이드 바인딩
- 개발자 및 AI 에이전트의 코드 변경 기준을 확고히 다지기 위해, 프로젝트 최상위 규칙인 [AGENTS.md](file:///Users/mj/workspace/playground/rag-proving-ground/AGENTS.md) 파일에 해당 레이어 경계 규칙(`Layering Boundaries`)을 상세 명문화함.

## 근거 및 대안 비교 (Rationale & Alternatives)

### 1. 대안 1: 모든 RAG 작업을 백엔드 API로 제공하고 그래프는 순수 오케스트레이션만 담당 (SDK 방식)
- **배제 이유**:
  - 그래프 내부의 매 단계(질의 재작성 $\rightarrow$ 검색 $\rightarrow$ 요약 $\rightarrow$ 가드레일)마다 개별 HTTP 홉이 추가되어 네트워크 레이턴시가 누적됨.
  - 요약 및 최종 생성 시 발생하는 LLM 토큰 스트리밍을 `Backend -> Graph(Aegra) -> Web` 순서로 복잡하게 프록싱해야 하므로 기술적 오버헤드가 지나치게 높음.
  - 무엇보다 RAG 실험 및 서빙 스캐폴드로서, 프롬프트 템플릿의 소소한 변경조차 백엔드 코드와 API 명세를 거쳐야 하므로 실험 사이클이 무거워지고 생산성이 크게 훼손됨.

### 2. 대안 2: 그래프도 직접 DB/벡터스토어 커넥션을 맺고 retrieval 수행
- **배제 이유**:
  - 보안 자격 증명 관리가 파편화되고, 백엔드와 그래프 두 군데 모두에서 데이터베이스 드라이버와 커넥션 풀을 제각각 조율해야 하므로 자원 낭비와 관리 복잡도가 증가함.

## 파급 효과 (Consequences)

* **긍정적 효과**:
  - **선명한 설계 경계**: DB 연결 필요 여부라는 간명한 단일 기준으로 구현 위치에 대한 회색지대를 완전히 해소함.
  - **네이티브 스트리밍 유지**: 그래프 런타임에서 LLM을 직접 Invoke하므로, Aegra/CopilotKit의 스트리밍 프레임워크를 수정 없이 네이티브로 백분 활용 가능.
  - **빠른 프롬프트 튜닝**: 에이전틱 RAG 흐름의 핵심인 프롬프트 제어권과 요약 흐름 설계 권한이 `graphs` 패키지에 유지되어, 백엔드 배포 없이도 신속한 RAG 파이프라인 실험이 가능함.
* **부정적 효과 및 완화 조치**:
  - `rag_core`가 무거워질 경우 그래프 서버에 일부 불필요한 의존성이 설치될 수 있음.
  - **완화 조치**: 향후 필요할 경우 `rag_core` 패키지 구성 시 필수 의존성과 선택적 의존성(예: DB 드라이버, Heavy 파서 등)을 `pyproject.toml` extra dependencies로 점진적으로 분리하여 그래프 서빙 런타임 패키지를 가볍게 유지함.
