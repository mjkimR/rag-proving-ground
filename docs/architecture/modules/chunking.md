# 텍스트 전처리 및 Semantic Chunking 파이프라인

## **0. 개요: 고성능 파서 중심의 청킹 단순화 (Semantic-First)**

최신 RAG 아키텍처의 핵심은 **고성능 구조화 파서(Semantic Parser, 예: Docling)의 결과물을 전적으로 신뢰하고, 이후의 청킹 로직을 최대한 단순화·평탄화(Flatten)하는 것**입니다.

* **파싱이 곧 1차 청킹:** 복잡한 Parent-Child 트리 구조를 DB 레이어에 억지로 구현하는 오버엔지니어링을 배제합니다. 파서가 레이아웃을 분석해 분리해 준 논리적 구조(DOM 트리) 자체를 가장 훌륭한 '독립적 의미 단위(Semantic Unit)'로 간주합니다.
* **문맥의 평탄화 (Context Flattening):** 분할로 인해 잃어버린 상하 문맥은 상위 목차(메타데이터)를 하위 본문 텍스트 맨 앞에 기계적으로 이어 붙이는 방식으로 단일 청크 내에서 단순하게 해결합니다.
* **방어적 후처리:** 결과적으로 텍스트 스플리터(Text Splitter)의 역할은 무조건적인 분할이 아닙니다. 파서의 결과물을 바탕으로 ① 과도하게 파편화된 조각 병합, ② 이미지 요소 보호, ③ 임베딩 한계를 초과하는 예외적인 덩어리의 '방어적 절단'만 수행하는 가벼운 후처리 파이프라인으로 동작합니다.

## **1. 아키텍처 개요**

본 시스템은 최신 RAG 환경의 검색 품질을 극대화하기 위해 '투 트랙(Dual Track)' 전략을 채택합니다.

* **Track 1 (텍스트 기반 검색):** 의미론적 구조 파싱(Semantic Parsing) 기반의 텍스트 청킹 및 임베딩 **(현재 구현 완료)**
* **Track 2 (비전 기반 검색):** ColPali 기반의 렌더링 이미지 검색 및 멀티모달 앙상블 **(TODO)**

**Track 1**의 상세 구현 사항을 정의합니다.

## **2. 핵심 처리 전략 (Track 1)**

파서(Parser)가 추출한 DOM 트리 요소를 기반으로, LLM이 이해하기 쉬운 독립적 의미 단위(Semantic Unit)를 구성합니다.

### **2.1. Breadcrumb (메타데이터 경로) 주입**

* **목적:** 문서가 잘게 분할되더라도 상하 문맥(Context)을 잃지 않도록 보호.
* **구현:** `_trim_breadcrumb` 로직을 통해 상위 대제목/소제목을 추출하고, 자식 노드 텍스트 맨 앞에 꼬리표처럼 접두어(`>`)로 이어 붙입니다.

### **2.2. 과도한 파편화 방지 (Sibling Merging)**

* **목적:** 글머리 기호(List Item)나 각주(Footnote) 등 쪼개지기 쉬운 미세 청크(Micro-chunks)들을 하나로 병합.
* **구현:** `ChunkingConfig`에 정의된 `merge_max_chars` (기본 300자) 한도 내에서, 동일한 부모 계층과 동일한 페이지 번호를 가진 요소들을 버퍼(Buffer)를 활용해 병합합니다.

### **2.3. 방어적 텍스트 분할 (Fallback Splitting)**

* **목적:** 버퍼 병합 후에도 임베딩 모델의 한계를 초과하는 대형 텍스트 블록의 안전한 절단.
* **구현:** `RAGFallbackTextSplitter`를 적용하여 단락, 줄바꿈, 문장 단위 순으로 쪼갭니다.
* **특이사항 (이미지 보호):** 텍스트 내 Markdown 이미지 링크 URL이 잘려서 손상되는 것을 방지하기 위해 분할 전 고유 ID(`__IMG_0000__`)로 치환(Placeholder) 후, 분할 완료 시 복원합니다.

## **3. Edge Case 대응: 페이지 경계 탐색 (Navigation Metadata)**

순수 텍스트 청킹의 단점인 "경계선에서의 문맥 단절"을 해결하기 위해 검색(Retrieval) 시점에 활용할 수 있는 풍부한 네비게이션 메타데이터를 각 청크에 삽입합니다.

* **기본 검색 전략:** 특정 청크가 검색되면, 해당 청크가 속한 **페이지(Page) 전체를 복원**하여 LLM에 제공.
* **경계선(Edge case) 확장 로직:**
* 검색된 청크에 `is_first_chunk_on_page=True`가 포함된 경우: 이전 페이지의 마지막 문맥이 필요할 수 있으므로 `previous_chunk_id`를 활용해 인접 청크를 추가 로드합니다.
* 검색된 청크에 `is_last_chunk_on_page=True`가 포함된 경우: 다음 페이지로 문맥이 이어질 수 있으므로 `next_chunk_id`를 활용해 인접 청크를 추가 로드합니다.

## **4. 향후 로드맵 및 TODO**

현재는 다른 RAG 시스템 구현 먼저 작업하기 위해 Track 1 부분만 구현 후 향후에 추가 확장할 예정입니다.

* **[Feature] Table 요약화:** `ElementType.TABLE`을 식별하여 LLM 기반 요약 텍스트를 메타데이터로 사전 주입하는 파이프라인 구성.
* **[Feature] 가성비 중심의 Contextual Retrieval (Anthropic 방식 변형):** 토큰 비용을 최적화한 문서 요약 및 청크 컨텍스트 합성 파이프라인 구축.
* **[Track 2] ColPali 파이프라인 통합 (하이브리드 비전 RAG):**
* 파싱 불가능한 복잡한 도표나 차트를 위해 문서 페이지 단위의 렌더링 파이프라인 구축.
* 검색 시 ColPali로 이미지를 리트리브한 후, 매핑된 파서 텍스트를 LLM에 전달하는 Decoupled Architecture 구현.

### 토큰 기반 분할(Tiktoken Encoder) 적용 여부

* **설계 문서:** 한국어 최적화 스플리터 세팅 시 `RecursiveCharacterTextSplitter.from_tiktoken_encoder`를 사용하여 임베딩 모델의 토큰 제한에 맞출 것을 명시했습니다.
* **현재 구현:** `recursive.py`의 `RAGFallbackTextSplitter`는 기본 `RecursiveCharacterTextSplitter`의 `__init__`을 상속받아 사용 중이므로, 토큰 단위가 아닌 '글자 수(Character length)' 기준으로 청크 사이즈(450)가 계산됩니다.
* **개선 제안:** 토큰 기반 길이 계산을 원한다면, 초기화 로직에서 `from_tiktoken_encoder` 팩토리 메서드를 오버라이딩하거나 커스텀 `length_function`에 `tiktoken`을 연결하는 방식이 필요합니다.

### 표(Table) 데이터의 LLM 자연어 요약 파이프라인

* **설계 문서:** 표 구조의 맥락을 살리기 위해 자연어 요약본을 생성하여 임베딩하는 방식을 추천했습니다.
* **현재 구현:** 현재 코드는 `_element_text`에서 표 데이터를 단순히 문자열로 추출할 뿐, LLM을 거치는 요약 처리 로직은 없습니다.
* **개선 제안:** 구조를 복잡하게 만들고 싶지 않다면 일단은 현재 상태를 유지하되, 향후 콜백(Callback)이나 별도 전처리 파이프라인에서 Table Element를 가로채어 요약본을 주입할 수 있는 확장 포인트(Hook)를 열어두는 것이 좋습니다.

### Anthropic식 Contextual Retrieval의 비용 최적화 변형 구현

* **설계 문서:** 청크 분할 시 문맥 소실을 막기 위해 각 청크마다 문서 전체의 맥락을 LLM으로 생성하여 주입하는 Anthropic의 'Contextual Retrieval' 기법이 제안되었습니다.
* **현재 제한 사항:** 청크마다 전체 문서를 매번 컨텍스트로 전달할 경우, 토큰 소비와 API 비용 감당이 어렵다는 치명적인 현실적 문제가 있습니다.
* **개선 및 실험 제안:** 100% 그대로 구현하는 대신 토큰 효율성을 극대화한 하이브리드 파이프라인을 구축합니다.

1. **문서 선(先) 요약:** 전체 문서를 LLM을 통해 고차원적으로 요약(Summary)합니다. (LlamaIndex의 요약/인덱스 관련 모듈 활용 검토)
2. **컨텍스트 합성 프로세스:** 전체 문서 요약본과 개별 청킹 텍스트를 조합하여 1차 가공합니다. 이때 검색 품질 향상을 위해 '현재 페이지(Page-level)의 맥락'까지 중간 레이어로 끼워 넣을지 여부는 추가 벤치마크 실험 후 확정합니다.
3. **코드 유연성:** 현재 `RAGSemanticChunker` 내부가 구조화된 블록(`_SemanticBlock`) 단위로 처리 흐름이 명확하게 쪼개져 있어, 해당 요약 및 컨텍스트 주입 레이어를 확장하는 작업은 큰 공수 없이 아키텍처 내에 통합 가능할 것으로 판단됩니다.
